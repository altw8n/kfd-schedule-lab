# «Ничего не падает» — работа с расписанием

Консольное приложение на Kotlin для обработки расписания. Оно читает файл, выбирает занятия по дате или типу и сообщает об ошибках входных строк. Реализованы модель занятий с проверками, реестр в памяти, журналирование через делегирование и разбор ошибок как данных.

Команды:

- `period` — корректные занятия в диапазоне дат включительно, без преподавателей;
- `type` — корректные занятия указанного типа, с преподавателями;
- `errors` — причины отклонения строк и их количество.

Порядок файла сохраняется. Все команды проверяют весь файл, даже если занятие не попадает в фильтр. Код завершения: `0` — отказов нет, `1` — есть отклонённые строки, `2` — неверные аргументы или ошибка чтения.

- [Условие задания](docs/assignment.md): требования, формат файла и вывода.
- [Памятка](docs/student-guide.md): готовый запуск, чтение строк, защита коллекций и тесты.

## Структура проекта

Исходный код находится в `app/src/main/kotlin/schedule/`, тесты — в `app/src/test/kotlin/schedule/`.

| Файл | Назначение |
|---|---|
| `Main.kt`, `Cli.kt`, `FileLines.kt` | запуск, аргументы и чтение файла |
| `Commands.kt` | Обработка команд и форматирование выбранных занятий |
| `Session.kt` | Интерфейс `Session` и четыре типа занятий |
| `SessionValidation.kt` | Проверки ограничений модели |
| `SessionRepository.kt` | Контракт реестра и хранение занятий в памяти |
| `Audit.kt` | События журнала и аудируемая обёртка реестра |
| `ScheduleLineParser.kt` | Разбор одной строки и выбор первой причины отказа |
| `ParseResult.kt`, `RejectionReason.kt` | Результаты разбора, причины отказов и обозначения полей |
| `RejectionFormatter.kt` | Английские сообщения и экранирование значений |

Реестр и аудит реализованы как отдельная часть задания. Команды обрабатывают строки сразу при чтении и не накапливают все занятия в реестре.

## Формат входного файла

Каждая строка содержит ровно пять полей, преподаватели разделяются запятыми:

```text
date|type|topic|location|teachers
2026-10-05|LECTURE|Classes and delegation|Room 312|Portnov
2026-10-08|PRACTICE|Domain modeling|Room 312|Anokhin
2026-10-15|EXAM|Oral exam 1|Room 401|Portnov,Stepanova
2026-10-19|CANCELLED|Lecture postponed|-|-
```

У отмены место и преподаватели обозначаются `-`. Пустая строка считается ошибочной, пустой файл допустим. Завершающий перевод строки не создаёт дополнительной строки.

## Начало работы

1. Клонируйте репозиторий и откройте его корневую папку в IntelliJ IDEA.
2. Установите **JDK 25**. Укажите его в `JAVA_HOME` и выберите JDK 25 для Gradle в IntelliJ IDEA.
3. Для генератора и проверки примеров нужен **Python 3.10+**.
4. Дождитесь импорта Gradle-проекта и загрузки зависимостей.

В проекте используются Kotlin **2.4.10**, Gradle **9.5.1** и JUnit **6.1.3**. Kotlin и Gradle отдельно устанавливать не нужно: используйте Gradle Wrapper. Первая сборка загружает зависимости из интернета.

Команды, типы в файлах, сообщения и примеры вывода — на английском. Учебные темы, места и имена записаны латиницей. Отсутствующее значение обозначается `-`.

## Сборка и запуск

Откройте Terminal в IntelliJ IDEA или отдельный терминал **в корне проекта**, где находятся `gradlew.bat`, `settings.gradle.kts` и `samples/`. На Windows вместо `python` можно использовать `py -3`; на Linux/macOS — `python3`.

Windows PowerShell:

```powershell
.\gradlew.bat build :app:installDist
.\app\build\install\schedule\bin\schedule.bat period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13
.\app\build\install\schedule\bin\schedule.bat type --file samples/dirty.txt --type EXAM
.\app\build\install\schedule\bin\schedule.bat errors --file samples/dirty.txt
```

Linux/macOS:

```bash
bash ./gradlew build :app:installDist
./app/build/install/schedule/bin/schedule period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13
./app/build/install/schedule/bin/schedule type --file samples/dirty.txt --type EXAM
./app/build/install/schedule/bin/schedule errors --file samples/dirty.txt
```

`build` компилирует приложение и выполняет тесты. `installDist` создаёт скрипты запуска. Условное имя `schedule` в задании обозначает это приложение: терминал сам по себе такой команды не знает.

Во время разработки можно запускать через Gradle:

```powershell
.\gradlew.bat :app:run --args="period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13"
```

Аргументы получает `main(args)`, после их проверки вызывается обработчик команды. Относительный путь к файлу отсчитывается от рабочей папки. Путь с пробелами заключайте в кавычки при запуске скрипта приложения.

Для проверки кодов завершения используйте скрипт приложения или `tools/verify.py`: при коде `1` или `2` команда Gradle `run` дополнительно сообщает о неуспешном завершении процесса.

## Проверка решения

На Linux/macOS выполните:

```bash
bash ./gradlew build :app:installDist
python3 tools/check_samples.py
python3 tools/verify.py
```

На Windows используйте `.\gradlew.bat build :app:installDist`, затем `python tools/check_samples.py` и `python tools/verify.py`.

Отдельный запуск всех JUnit-тестов: `bash ./gradlew test` или `.\gradlew.bat test`. Только готовые тесты преподавателя: `bash ./gradlew :app:test --tests "schedule.CliTest"`.

Проверяются небольшие файлы, вывод всех четырёх типов, октябрьский диапазон, ошибки аргументов и чтения. Сравниваются текст и коды завершения; LF и CRLF в выводе считаются эквивалентными. Отчёт сохраняется в `verification/acceptance.json`.

| Входной файл | Содержание |
|---|---|
| `samples/clean.txt` | 200 корректных строк |
| `samples/dirty.txt` | 500 строк, 164 отказа |
| `samples/empty.txt` | Ни одной строки |

В `samples/*.expected` находятся эталоны. `clean.expected` — полный диапазон для `period`. Эталоны `*.type.expected` относятся к `--type EXAM`. `dirty.october.expected` — `period` с `--from 2026-10-01 --to 2026-10-31`; код завершения `1`, поскольку проверяется весь файл.

Собственные тесты проверяют инварианты модели, защиту списков, делегирование, приоритет ошибок и границы фильтров. Совпадение с эталонами не заменяет эти проверки.

### GitHub Actions

На push и pull request запускаются сборка, тесты и проверка согласованности примеров на Windows и Linux. Базовая проверка проходит уже в шаблоне: она проверяет готовый код и написанные вами тесты, **но не подтверждает выполнение всей лабораторной**.

Для полного сравнения вывода откройте Actions → schedule-lab → Run workflow и включите `acceptance`. Для большого файла дополнительно включите `huge`.

**Автоматические проверки предназначены для самопроверки.** В репозитории уже есть тесты готового запуска и сравнение вывода с эталонами на заданных примерах. Их успешное прохождение помогает понять, что основные проверяемые сценарии, скорее всего, реализованы верно. Но это ограниченный набор тестов: он не доказывает правильность решения во всех случаях и не означает автоматическую сдачу работы.

**Основную проверку и итоговую оценку проводит лабник.** Он изучает код, проверяет устройство модели, соблюдение инвариантов, защиту коллекций, делегирование, обработку ошибок и пограничные случаи. Собственные тесты и объяснение принятых решений остаются обязательной частью работы.

## Выбор типов и проверки модели

`Session` — sealed-интерфейс с общими свойствами `date` и `topic`. Его варианты: `Lecture`, `Practice`, `Exam` и `Cancelled`. Sealed-иерархия позволяет компилятору проверять полноту обработки вариантов в `when`.

Для занятий выбраны обычные классы. Автоматические `copy()`, декомпозиция и сравнение по содержимому для этой реализации не требуются. Обычный класс не создаёт дополнительного метода `copy()`, безопасность которого пришлось бы отдельно проверять. Использовать `data class` тоже возможно, но тогда конструктор и `copy()` должны сохранять все инварианты.

У `Cancelled` есть только дата и тема. Свойств места и преподавателей у него нет, поэтому отсутствие этих данных выражено устройством типа, а не `null`.

Дата хранится как `LocalDate`: этот тип представляет существующую календарную дату. Дополнительно модель ограничивает год диапазоном `1..9999`. Преподаватели хранятся списком, потому что их порядок должен сохраняться. Множество применяется только для проверки уникальности.

Каждый конструктор через `init` вызывает функции из `SessionValidation.kt`. Проверяются непустые значения, отсутствие внешних пробелов и управляющих символов, допустимость места и имён, количество преподавателей и отсутствие повторов. Нарушение приводит к `IllegalArgumentException`, в том числе при прямом создании объекта без парсера. Значения не обрезаются и не исправляются; `Ivanov` и `ivanov` считаются разными именами.

Для причин отказов, результатов разбора и событий аудита используются `data class`: они хранят данные, и их удобно сравнивать в тестах. Причины без дополнительных данных представлены `data object`. Для названий полей и операций применены enum, чтобы исключить опечатки в строковых обозначениях.

## Защита коллекций

`val` запрещает переприсваивать ссылку, но сам по себе не защищает изменяемый список. Поэтому конструкторы занятий сохраняют преподавателей через `java.util.List.copyOf` и проверяют сохранённую копию. Изменение исходного `MutableList` не влияет на занятие. Полученный через свойство список неизменяем: попытка добавить или удалить элемент приводит к `UnsupportedOperationException`.

Реестр хранит занятия в закрытом изменяемом списке. `all()` возвращает независимый неизменяемый снимок через `List.copyOf`. Последующие добавления не меняют ранее полученный снимок. Порядок сохраняется, одинаковые занятия допускаются. Свойство `auditEvents` аналогично выдаёт снимок журнала.

## Делегирование и аудит

`AuditedSessionRepository` реализует `SessionRepository by delegate`: хранением занимается переданный реестр, а обёртка добавляет журналирование. Методы `add` и `addAll` переопределены; `all` автоматически передаётся делегату.

Переопределить только `add` недостаточно: вызов `addAll` тогда уйдёт напрямую в делегат и не создаст событие в обёртке. Даже если делегат реализует `addAll` через собственный `add`, внутренний вызов относится к делегату, а не к обёртке.

Событие записывается после успешного завершения вызова делегата. `add` создаёт одно событие с количеством `1`, `addAll` — одно событие с размером списка. Пустой пакет создаёт событие с количеством `0`. `totalAdded` считает добавленные через обёртку занятия. При исключении журнал и счётчик не обновляются. `all()` не создаёт событий. Журнал хранится в памяти и автоматически не печатается.

## Разбор строк и сообщения

Парсер возвращает `ParseResult.Success` с занятием или `ParseResult.Rejected` с номером строки и структурированной причиной. Готовый текст сообщения и `Throwable` вместо причины не хранятся. Ошибочная строка не прерывает обработку следующих строк.

Проверки выполняются в порядке из условия: разделитель, количество полей, первое пустое поле, дата, тип, количество преподавателей экзамена, затем остальные ограничения. Среди последних сначала проверяются управляющие символы, внешние пробелы, поля отмены, место действующего занятия, недопустимые преподаватели и дубликаты. Для строки выбирается одна причина.

`formatRejection` отдельно превращает отказ в английское сообщение. Шесть обязательных формулировок сохранены из условия. Для остальных причин используются следующие сообщения; `N`, имя поля и значение подставляются из отказа:

```text
line N: field "topic" contains control characters: "..."
line N: field "topic" has leading or trailing whitespace: "..."
line N: type "CANCELLED" requires "location" to be "-", got "..."
line N: invalid location "..."
line N: invalid teacher "..."
line N: duplicate teacher "..."
```

В сообщениях об управляющих символах и внешних пробелах имя поля зависит от причины. Для отмены проверяются `location` и `teachers`. Вставляемые значения экранируются: `\` превращается в `\\`, `"` — в `\"`, управляющие и не-ASCII символы — в `\uXXXX` для каждого UTF-16 символа. Это преобразование относится только к выводу, исходные значения модели не изменяются.

## Попытки сломать модель и тесты

В `SessionTest.kt` проверяются следующие попытки нарушения контракта:

| Попытка | Механизм защиты |
|---|---|
| Пустая тема | Проверка в конструкторе, `IllegalArgumentException` |
| Год `0` или `10000` | Проверка диапазона года в конструкторе |
| Лекция или практикум без преподавателей | Проверка минимального количества |
| Экзамен с одним преподавателем | Требование минимум двух преподавателей |
| Экзамен с одинаковыми преподавателями | Проверка уникальности имён |
| Очистка исходного списка после создания | Независимая копия преподавателей |
| Изменение списка через публичное свойство | Неизменяемый список, `UnsupportedOperationException` |
| Обход через `copy()` | У классов занятий такого метода нет; отдельный тест не требуется |

Также проверяются корректное создание всех четырёх типов, запрет `-` для места и имени действующего занятия и различие регистра имён.

Другие тестовые файлы:

- `CliTest.kt` — готовые тесты преподавателя для аргументов, запуска и чтения;
- `SessionRepositoryTest.kt` — порядок, дубликаты, пустой пакет и защита снимков;
- `AuditedSessionRepositoryTest.kt` — одиночный и пакетный аудит, пустой пакет, ошибки делегата и отсутствие повторного журналирования;
- `ScheduleLineParserTest.kt` — четыре типа, конечные пустые поля и приоритет нескольких ошибок;
- `CommandsTest.kt` — включительность границ дат, порядок файла, нулевой результат, отказы вне фильтра, пустой файл и CRLF.

Тесты проверяют конкретные сценарии и не доказывают корректность для всех возможных входов. Дополнительная операция переноса занятия со звёздочкой не реализована.
